# `lib/` File Specifications

This directory is the file-by-file implementation contract for Flutter source under `lib/`. Use it to implement the project without having to invent module boundaries, class responsibilities, or expected behavior. The specification is for `cmu_sbnu_vms`; the `nsrc_vms` tree is reference material only. Target decisions and approved requirements override this catalog.

## How to use this catalog

1. Read [the implementation guide](../architecture/implementation-guide.md) and the target repository's current README and approved decision records.
2. Implement one vertical slice at a time in the order in §Implementation order below. Do not start a feature until its prerequisite contracts and policy decisions exist.
3. Create only source files called for by the selected slice. Each specified file below names its intended public types, duties, allowed dependencies and required tests. If a design needs to change, update this catalog and record why before relying on the new design.
4. Keep platform generated files generated. `lib/firebase_options.dart` is generated by FlutterFire for the target Firebase project; never author credentials into it manually.
5. Every feature slice must include its page states, validation, repository methods, server authorization, negative permission tests, and documentation updates. A screen alone is not a complete slice.

Test cases described in these specifications define desired acceptance/CI coverage; they do not authorize an AI agent to add or execute tests. Follow the explicit test authorization rule in root `AGENTS.md`. If required coverage is not authorized, report it as pending evidence.

## Cross-file rules

- Use `package:cmu_sbnu_vms/...` imports, not relative parent-directory chains. Keep files under the feature that owns their behavior.
- Screens are presentation-only. They may read a controller/provider and call intent methods; they do not access `FirebaseFirestore`, `FirebaseAuth`, raw document maps, or platform channels directly.
- Controllers/providers own view state and orchestration. Repositories own query/write mapping and cache policy. Services wrap a particular external SDK. Models own parsing and invariants.
- A repository call returns a typed outcome or throws a documented domain exception. Do not convert network/auth failures to empty lists. Render loading, empty, stale/offline, and error states distinctly.
- Constructors accept dependencies explicitly. Avoid hidden global Firebase access in feature code. `FirebaseFirestore.instance` and `FirebaseAuth.instance` belong in composition/bootstrap or concrete service adapters.
- All timestamps persisted to Firestore are UTC/server timestamps. UI formats to the user's locale/timezone. Date-only business rules define the unit timezone explicitly.
- No client-controlled role, account approval, actor UID, audit timestamp, service-hour total, incident responder identity, QR validity, or notification authorization is trusted by backend logic.
- Do not put personal or incident details in logs, analytics labels, exception strings, crash reports, URLs, QR contents, or test fixtures.
- Generated files, platform host files and Firebase configuration are not part of the handwritten `lib/` contracts, except the generated target options file.

## Documentation completeness rule

The specifications below enumerate the initial production scope and expected source files, not a requirement to create empty files. Feature-local subwidgets/controllers can be split when an implementation warrants it; document any added file in the matching module section. When an existing scaffold folder is intentionally deferred, retain the folder's TODO and record the reason in the implementation tracker. Before calling a feature complete, its section must have source paths, a test reference, and no unexplained placeholder behavior.
